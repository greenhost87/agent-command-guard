# План: сохранять inline-код при отказе гейта

## Цель и границы

Когда агент уже отправил `node -e '...'` или `python3 -c '...'`, не заставлять его повторно выводить код ради создания файла. Если гейт может **однозначно** восстановить исходный текст программы, он сам сохраняет её в `.codex/tmp-scripts/` текущего workspace, всё равно отклоняет исходную команду и сообщает путь к файлу. Следующий вызов инструмента запускает файл отдельной командой, которая проходит обычную проверку политики. Код не выводится повторно и никогда не исполняется хуком.

Первая версия: только простой самостоятельный вызов Node (`-e`, `--eval`, `--eval=...`) или Python (`-c`) с одним литеральным аргументом-кодом. Остальные причины отказа и остальные формы inline-кода, включая `node -p`, shell `-c`, stdin/heredoc, цепочки команд и вложенные command substitutions, остаются без сохранения. Расширять список можно отдельно, после тестов точного извлечения и эквивалентности запуска.

## Точки изменений

- `cmd/agent-command-guard/interpreter_policy.go`, `install_policy.go`, `shell_parse.go`: после определения причины отказа получить данные для сохранения только при *фактическом* отказе `inlineInterpreterReason`; не заменять детекцию запрета новой, более узкой детекцией сохраняемых команд. Текущие `shellToken.value` и `commandSpan` полезны для поиска интерпретатора, но точность декодирования аргумента для записи нужно проверять отдельно.
- `cmd/agent-command-guard/hook_output.go`, `cursor.go`: общий путь принятия решения и сохранения для Codex и Cursor; добавить путь к сохранённому файлу в текст отказа, не меняя JSON-схемы. Не применять к patch/file/search событиям. `adapters/pi/extension.ts` уже передаёт `permissionDecisionReason` пользователю/агенту и не должен дублировать сохранение.
- `cmd/agent-command-guard/config/policy.json`: оставить `.codex/tmp-scripts/` каталогом аудита; при необходимости уточнить guidance: «readable» означает читаемый владельцем файл `0600`, который оставляют для проверки.

## Последовательность реализации

1. Сохранить существующий порядок проверок. Сначала вычислить обычное решение политики; запись возможна лишь когда окончательная причина отказа — inline-код, без подмены других причин (например, доступа к защищённым путям или отменённой установки). Возвратить прежний отказ, если сохранение не подходит или не удалось.
2. Реализовать консервативное извлечение из **исходной строки команды**: единственный простой вызов интерпретатора без пайпов, `;`, `&&`, редиректов, присваиваний окружения, подстановок `$()`, обратных кавычек или иных shell-операторов; один однозначный аргумент-код после поддерживаемого флага либо в `--eval=...`. Учитывать опции перед флагом только там, где их разбор однозначен. Раскрывать shell-кавычки/экранирование без исполнения shell; принимать только формы, для которых можно доказать точное совпадение байтов с аргументом, который получил бы интерпретатор. Динамическое расширение переменных, незакрытые кавычки, неоднозначные escaping/флаги, несколько inline-программ или отсутствие аргумента — отказ без файла. Не использовать содержимое командной строки как имя файла.
3. Записывать извлечённый код в уникальный файл `.js` / `.py` под `<cwd>/.codex/tmp-scripts/`. Проверять непустой абсолютный `cwd`, существование workspace и то, что каталог назначения и его компоненты не являются symlink; не следовать symlink при создании файла. Создавать недостающий каталог с ограниченными правами, открывать файл только на создание (`O_EXCL`) с режимом `0600`, закрывать и удалять неполный файл при ошибке записи. Не перезаписывать и не удалять ранее сохранённые audit-файлы. Если безопасную запись гарантировать нельзя — обычный отказ без пути.
4. Дополнить текст отказа короткой инструкцией: `Saved inline code to <относительный путь>; original command was not run. Run as a file after reviewing it.` Для успешного сохранения убрать из `denialMessage` превью исходной команды (сейчас оно включает первые 50 символов и может повторять код); оставить только причину и путь. При неудаче не утверждать, что файл сохранён. При необходимости передавать исходные позиционные аргументы запуска отдельной командой: сначала поддержать лишь формы без них, чтобы не обещать полную эквивалентность `node -e`/`python -c` и запуска из файла (`process.argv`/`sys.argv`, рабочий каталог, особенности режима eval). Указать это ограничение в сообщении или guidance.
5. Сохранить формат ответа: Codex — `permissionDecision: deny` и `permissionDecisionReason`, Cursor — `permission: deny` с одинаковыми `user_message`/`agent_message`, Pi — `block: true` с той же причиной. Повторный запуск файла всегда проходит гейт заново; сохранение не означает разрешение на исполнение.

## Фикстуры из локальных логов

`/Users/greenhost/.agent-command-guard/` содержит JSONL-логи хуков (`acg.jsonl`, датированные `*-acg.jsonl`) в двух форматах: записи с `d`/`s` и старые с `data`/`status`. В них есть исходные команды, поэтому не копировать логи целиком в репозиторий, сообщения об ошибках или тестовые снапшоты: там могут быть секреты и личные пути. В конкретных файлах `2026-09-14-acg.jsonl` и `2026-09-24-acg.jsonl` на момент выборки было соответственно 1 920 отказов / 3 уникальные строки команды и 29 отказов / 29 уникальных строк; сегодняшние отказы Pi — 28 разных команд. Частоты и совпадение строк сами по себе не доказывают причину отказа или возможность безопасного извлечения кода.

Набор `cmd/agent-command-guard/testdata/inline_script_staging.json` содержит **обезличенные минимальные аналоги наблюдавшихся форм** `node -e` (двойные кавычки), `python -c` (одинарные и двойные кавычки), а также синтетические пограничные случаи. Это не дословные payload из логов. `want_code` задаёт ожидаемый текст файла; `null` значит «отказ без сохранения», а не «разрешить команду». Набор подключён к `inline_staging_test.go`; ошибки записи и права файлов проверяются отдельно в изолированном workspace. Оригиналы и полный payload хуков не коммитить.

## Тесты и проверка

- Go unit-тесты на точные байты файла (пробелы, переводы строк, кавычки, допустимое escaping), уникальность имён и права `0600`; тесты отрицательных случаев: динамические подстановки, цепочки/пайпы, несколько команд, некорректные кавычки/флаги, отсутствие `cwd`, symlink, невозможность записи. Проверить отсутствие файла при другом отказе и при безопасной команде.
- Интеграционные тесты Codex (`main_security_test.go`) и Cursor (`cursor_test.go`): код сохраняется в отдельном `t.TempDir()` workspace, отказ содержит реальный путь, схема JSON не меняется, исходная команда не исполняется. Тест Pi (`adapters/pi/extension.test.ts`): причина с путём доходит до `tool_call` без повторного вывода кода. Текущие тесты отказов для неподдерживаемых форм остаются зелёными.
- Поскольку затрагиваются `main.go`/`cursor.go` либо общий Go-хук, **до правок** зафиксировать `./scripts/benchmark.sh` и `wc -c build/agent-command-guard`; **после правок** выполнить `go test ./cmd/agent-command-guard`, повторить тот же benchmark и размер, сообщить значения до/после. Для Pi-тестов — `bun --cwd adapters/pi test`; если меняется `extension.ts`, дополнительно `./scripts/benchmark-pi.sh` по правилам проекта.

Критерий готовности: два простых вызова (`node -e '...'`, `python3 -c '...'`) требуют лишь следующей короткой команды с путём, а при любой неоднозначности или ошибке записи политика продолжает блокировать команду, не сообщая о несуществующем файле.
